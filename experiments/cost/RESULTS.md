## Три места, где токены почти есть — и почему не годятся

**1. `run_injecagent.py` — платные прогоны были, `usage` выброшен.**
Это самая близкая к цели точка: единственные реальные платные прогоны в кодовой базе,
и у них есть resumable per-case JSONL. Но `call_model` возвращает только текст:

```python
c = self.client.chat.completions.create(model=..., messages=..., temperature=0, max_tokens=1024)
if c and c.choices:
    return c.choices[0].message.content or ""     # <- объект c.usage отброшен
```

Запись в кэш содержит 8 полей — `User Tool`, `Attacker Tools`, `Tool Response`,
`Attacker Instruction`, `User Instruction`, `output`, `eval`,
`Attacker Tool Parameters` — ни одного про расход. Плюс `save_dir` был
CLI-аргументом, и сами JSONL в репозиторий не попали: на диске их нет.
Итог: деньги уже потрачены, а данные о расходе безвозвратно утеряны.

**2. `bundle.schema.json` — поля объявлены, их никто не заполняет.**
`tokens_in`/`tokens_out`/`cost_usd` живут только в схеме и в тестах с руками
вписанными значениями. Ни один адаптер (`lab_adapters/agentdojo.py`,
`fabrication.py`) их не выставляет, а описание самой схемы это фиксирует:
*«absent for a scripted/simulated agent that spends nothing measurable»*.
Тесты прямо утверждают отсутствие (`assertNotIn("cost_usd", case["metrics"])`).
То есть контракт готов, поставщика данных нет.

**3. `TokenMeter` — считает, но не сохраняет и теряет разбиение.**
`eval_budget.py` действительно читает `usage` из ответа API
(`usage_openai`: `total_tokens` или `prompt_tokens + completion_tokens`). Но:
`TokenMeter` — это `total: int`, то есть **input и output схлопнуты в один скаляр**;
он `reset()`-ится между прогонами; и `eval_budget.py` **не пишет ни одного файла**.
Для основной единицы задания `w = input + 4 × output` этого недостаточно в принципе:
коэффициент 4 неприменим к схлопнутой сумме.

## Результат, который получается без данных: фича 2 требует смены харнесса

Это не зависит от логирования и меняет постановку.

**На InjecAgent фича 2 невозможна по построению, даже с идеальными токенами.**
Две независимые причины:

1. *Нет чистого контрафакта.* InjecAgent — pure-attack бенчмарк: 1 054 кейса, и,
   как фиксирует README адаптера, *«There are **no benign tasks**»*. Сравнивать
   `w_attacked − w_clean` не с чем — парного чистого прогона того же user_task
   не существует.
2. *Армы совпадают потокенно.* Модель прогоняется **один раз** (undefended), а
   governance — детерминированный пост-фильтр, проигрывающий ту же траекторию
   (`govern_injecagent.py`). Governed и ungoverned получаются из *одних и тех же
   выходов*, значит их расход токенов **тождественно равен**. Разрез «по arm» из
   задания на этом харнессе даст ровно нули, и это свойство дизайна, а не выборки.

**На AgentDojo фича 2 возможна.** Там `run_benign(governed, suite)` собирает
отдельный pipeline на каждую арму (`build_pipeline(governed)`) и прогоняет модель
заново, то есть токены между армами действительно могут расходиться; и есть
бенигнный проход без атаки — то самое парное `clean` к `attacked`.

**Вывод для планирования:** инструментировать надо AgentDojo-адаптер, а не
InjecAgent. На InjecAgent стоит инструментировать расход только ради фич 1 и 3
(бюджет и прогноз суммы), для фичи 2 он непригоден независимо от логирования.

## Что минимально добавить в логирование

Правка маленькая и в одном стиле: сохранять `usage` там, где он уже приходит в
ответе, и дотянуть его до per-trial записи.

**(a) `axor-core/examples/agentdojo/run_agentdojo.py` — приоритет 1 (нужен всем трём фичам).**
Это единственный харнесс, где возможна фича 2. Обернуть вызов модели так, чтобы
из ответа забирались `usage.prompt_tokens`, `usage.completion_tokens` и, если
провайдер отдаёт, `usage.prompt_tokens_details.cached_tokens`; аккумулировать
**раздельно** (не скаляром) по прогону вместе со счётчиками `n_llm_calls`,
`n_tool_calls`; дописывать одну JSONL-строку на trial в каталог, который
коммитится. Минимальный набор полей ровно под раздел 2 задания:

```
trial_id, benchmark, suite, user_task, injection_task|none, attacked,
arm, model, provider, input_tokens, output_tokens, cached_tokens,
cost_usd|null, n_llm_calls, n_tool_calls, outcome, order_index
```

`order_index` — просто монотонный счётчик внутри прогона; он нужен для проверки
эффекта кэширования промптов из раздела 3C, и без него эту проверку сделать нельзя.

**(b) `axor-core/examples/injecagent/run_injecagent.py` — приоритет 2 (фичи 1 и 3).**
В `call_model` вернуть не только текст, но и `c.usage`; добавить эти поля в `rec`,
который и так пишется построчно. Правка в две строки, кэш уже есть. Плюс
коммитить `save_dir` (или задать его по умолчанию).

**(c) `axor-lab` — приоритет 3 (замкнуть контракт).**
Поставщик для уже объявленных `metrics.tokens_in/tokens_out/cost_usd`: адаптер
должен их выставлять, когда backend реальный, сохраняя текущее «absent» для
scripted-агентов. Тогда фича 3 считается прямо из bundle.

**(d) `trace.schema.json` — опционально.**
Если расход должен быть виден на уровне трассы ядра, а не только eval-харнесса,
в схему нужно добавить блок usage; сейчас его нет ни в каком виде. Для проверки
трёх фич это не обязательно — достаточно (a)–(c).

**Сколько данных нужно, чтобы проверка состоялась.** Из раздела 3 задания: класс =
`(suite, arm, attacked, model)`, и при < 20 прогонах класс приходится объединять;
холодный старт проверяется до K = 50, а фича 3 требует k = 10 пилотных плюс
N = 30 «будущих» **из того же класса, без пересечения**, то есть ≥ 40 прогонов на
ячейку. Значит минимально осмысленный сбор — порядка 40–50 прогонов на ячейку, и
ячеек нужно несколько, чтобы «в большинстве классов» из критерия A имело смысл.
Отдельно замечу: одного прогона AgentDojo на все армы не хватит — бенигнный и
атакованный проходы для фичи 2 должны быть парными по `user_task`.
